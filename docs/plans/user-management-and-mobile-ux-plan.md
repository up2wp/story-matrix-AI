# 用户管理与移动端体验改造计划

日期：2026-06-11

## 目标

把当前只有 `admin/user` 两级的用户系统，升级为清晰的 `owner/admin/user` 权限模型，并补齐用户管理、个人资料编辑、软删除和移动端竖屏可用性。

这份计划只描述实施路径，不直接修改代码。涉及数据库结构或数据迁移的步骤，实施前需要用户明确确认。

## 当前状态

- 默认账号由 `server/src/seed.ts` 创建，用户名为 `admin`，当前角色只是 `admin`，没有拥有者概念。
- 用户表定义在 `server/src/db.ts`，字段只有 `id`、`username`、`passwordHash`、`displayName`、`role`、`createdAt`，没有软删除或账号状态字段。
- `server/src/routes/users.ts` 中创建用户需要管理员，但查询、更新、删除只需要登录；这会导致任意登录用户都可能修改或删除其他用户。
- `src/pages/admin/AdminPage.tsx` 的用户管理只能新增和硬删除，不能编辑已有用户。
- `src/components/layout/TopBar.tsx` 的头像菜单只有修改密码和退出登录，没有个人资料编辑。
- `src/core/auth-store.ts` 的修改密码逻辑直接更新用户记录，没有服务端专用接口，也没有校验原密码。
- 移动端主要受全局 `overflow: hidden`、`100vh` 固定高度、默认展开侧边栏、固定宽弹窗/面板影响，导致竖屏浏览时内容和保存按钮不可达。

## 产品范围

### 角色与权限

- `owner`：默认 `admin` 账号升级为拥有者。拥有者可以创建、编辑、软删除管理员和普通用户，可以设置角色和重置密码。
- `admin`：可以创建、编辑、软删除普通用户，可以修改普通用户密码，但不能创建、编辑、删除管理员或拥有者。
- `user`：只能使用普通创作功能，并能编辑自己的显示名称和修改自己的密码。
- 拥有者不能被降级、软删除或硬删除。

### 用户管理

- 用户管理页支持创建用户、编辑用户、重置密码、设置角色、软删除用户。
- 编辑范围必须与创建范围一致：拥有者可管理 `admin/user`，管理员只可管理 `user`。
- 对无权限操作，前端不展示主操作入口；必要时以禁用状态和说明提示。
- 删除改为停用/软删除，不再直接硬删除用户记录。

### 个人资料

- 每个登录用户可从右上角头像菜单进入个人资料编辑。
- 本轮资料范围限定为显示名称/昵称，不加入头像上传、邮箱、手机号等完整账户资料体系。
- 修改密码应走服务端接口，并校验原密码。

### 移动端可用性

- 竖屏移动端必须能完成登录、注册、打开用户菜单、编辑个人资料、用户管理基础操作和表单保存。
- 内容较长时必须能滚动到底部，保存按钮不能被永久遮挡。
- 用户管理表格在移动端应优先变为卡片/紧凑列表，而不是强制用户横向拖表格。
- 复杂编辑器页面先保证不被布局锁死；不在本轮重做全部创作流程的移动端专属交互。

## 实施阶段

### 阶段 1：权限模型和服务端边界

1. 扩展用户角色类型，加入 `owner`。
2. 将默认 `admin` 账号升级为 `owner`，并保证已有部署的数据能识别该账号。
3. 在服务端建立统一权限判断，覆盖创建、编辑、重置密码、软删除、查看用户列表等动作。
4. 收紧 `server/src/routes/users.ts`：所有用户变更必须经过角色权限校验，不能只依赖 `requireAuth`。
5. 增加服务端修改自己资料和修改密码入口，避免前端直接写 `passwordHash`。

需要触碰的文件预计包括：

- `server/src/db.ts`
- `server/src/seed.ts`
- `server/src/middleware/auth.ts`
- `server/src/routes/auth.ts`
- `server/src/routes/users.ts`
- `src/core/types.ts`
- `src/core/auth-store.ts`

### 阶段 2：数据结构与软删除

此阶段需要用户批准，因为会改变数据库结构。

1. 为用户记录增加软删除/停用状态，例如删除时间或状态字段。
2. 列表默认隐藏已删除用户，必要时保留恢复入口。
3. 登录时阻止已软删除用户进入系统。
4. 删除用户时保留作品归属，不直接级联删除作品。
5. 明确拥有者保护：拥有者不能被停用、降级或删除。

需要触碰的文件预计包括：

- `server/src/db.ts`
- `server/src/routes/auth.ts`
- `server/src/routes/users.ts`
- `src/core/types.ts`
- `src/pages/admin/AdminPage.tsx`

### 阶段 3：用户管理前端

1. 重构 `src/pages/admin/AdminPage.tsx` 的用户管理区，支持新增和编辑共用一套表单。
2. 根据当前用户角色动态限制角色选项和可编辑字段。
3. 增加重置密码入口，避免在编辑用户时误改无关字段。
4. 将删除动作改为软删除/停用，并提供清晰确认文案。
5. 当前用户行保留保护提示，避免用户在管理页操作自己造成会话状态混乱。

需要触碰的文件预计包括：

- `src/pages/admin/AdminPage.tsx`
- `src/core/auth-store.ts`
- `src/core/api-client.ts`
- `src/core/types.ts`

### 阶段 4：头像菜单与个人资料

1. 在 `src/components/layout/TopBar.tsx` 的头像菜单中增加“个人资料”。
2. 提供显示名称编辑弹窗或抽屉。
3. 修改成功后刷新本地登录用户状态，保证顶栏立即显示新昵称。
4. 修改密码改为调用服务端接口，并校验原密码。

需要触碰的文件预计包括：

- `src/components/layout/TopBar.tsx`
- `src/core/auth-store.ts`
- `server/src/routes/auth.ts`

### 阶段 5：移动端竖屏可用性

1. 调整全局布局，避免 `html/body/#root` 和主布局链路把页面锁死在不可滚动状态。
2. 使用动态视口高度，减少移动端浏览器地址栏导致的 `100vh` 裁切问题。
3. 小屏下默认收起侧边栏，必要时改为抽屉式导航。
4. 固定宽弹窗改为移动端可用宽度，并确保弹窗主体可滚动、底部操作按钮可触达。
5. 用户管理列表在移动端使用卡片/紧凑布局，桌面端保留表格。
6. 对登录、注册、管理后台、用户菜单、关键保存表单做竖屏手动验证。

需要触碰的文件预计包括：

- `src/index.css`
- `src/components/layout/AppLayout.tsx`
- `src/components/layout/Sidebar.tsx`
- `src/components/layout/AIPanel.tsx`
- `src/components/layout/TopBar.tsx`
- `src/pages/admin/AdminPage.tsx`
- `src/pages/login/LoginPage.tsx`
- `src/pages/login/RegisterPage.tsx`

## 验证计划

### 自动验证

- `npm run test:model-config`
- `npm run build`
- `npm run lint`，如果发现大量历史 lint 问题，只修本次改动引入的问题并在交付说明中标注既有问题。

### 手动验证

- 使用默认 `admin/admin` 登录后，确认该账号显示为拥有者并可创建管理员和普通用户。
- 使用管理员账号登录，确认只能创建和编辑普通用户，不能创建管理员。
- 使用普通用户登录，确认不能进入系统管理页。
- 验证用户编辑：修改昵称、角色、重置密码、软删除。
- 验证个人资料：每个角色都能从头像菜单修改自己的显示名称和密码。
- 验证软删除：被删除用户无法登录，列表中状态清晰，拥有者不可删除。
- 在手机竖屏尺寸验证登录、注册、管理后台、用户编辑、保存按钮可达。

## 风险与依赖

- 数据库结构变更是红线操作，实施前必须获得用户明确批准。
- 现有会话中只记录 `userId`、`username`、`role`，角色变更后旧会话的权限是否即时生效需要在实现阶段处理。
- 当前作品接口也缺少服务端所有权校验；如果只修用户管理，权限模型仍不完整。建议作为同一轮安全收敛的一部分处理，或明确拆成后续任务。
- 修改全局移动端布局可能影响章节编辑、预览、AI 面板等复杂页面，需要逐页验证。

## 暂不纳入本轮

- 自定义权限矩阵或按用户单独授权。
- 多组织、多租户或团队空间。
- 审计日志。
- 头像上传、邮箱、手机号、通知偏好等完整账户设置。
- 全部创作流程的移动端原生重设计。

## 推荐执行顺序

1. 先取得数据库结构变更批准。
2. 实施服务端权限模型和用户软删除。
3. 补齐用户管理前端和个人资料编辑。
4. 修复移动端壳层和用户管理页移动端体验。
5. 再评估是否将作品接口所有权校验纳入同一轮。
